# Decisions

These are settled. Don't reopen them unless the user asks. Newest first.

- **2026-10-12: How a download is written to disk (Phase 3).** The file is created as `<name>.part` in the user's Downloads folder, and renamed to `<name>` only once every byte is written and flushed. It's one file renamed, not parts joined. Names come from `Content-Disposition` or the URL, cleaned for Windows (no folders, reserved characters or device names, at most 200 characters), and " (1)", " (2)"... is added rather than overwriting anything. When the size is known, the whole size is claimed up front with `SetFileInformationByHandle(FileAllocationInfo)` and then `SetEndOfFile`, after a free-space check, so a full disk fails at once with a clear message. Writes are positioned `WriteAt` calls from each stream; the file records which byte spans are written and refuses to finish while any is missing. **Measured** (1 GiB file, NVMe, Ryzen 9 9950X, 256 KiB writes, 4 and 8 writers): reserved + `WriteAt` about 1.6 GB/s, sparse + `WriteAt` about 1.7-1.8 GB/s, reserved + mmap about 2.3-2.4 GB/s. All three are far above any internet line, so `WriteAt` stays: it is fast enough, and a full disk or a lost network drive comes back as an error instead of crashing the process as mmap would. Sparse files aren't used, which replaces the earlier `FSCTL_SET_SPARSE` plan: they don't reserve space, so a full disk shows up mid-download. The cost of not using them is that NTFS fills the gap with zeros the first time a part writes far into the file (measured: about 0.5 s for a write 3 GiB in). That happens once per file and only stalls that one stream.
- **2026-10-12: How HLS and DASH streams are downloaded (Phase 4).** The engine reads the manifest the extension sent, or fetches it, along with any variant playlists, using the browser's headers. Cookies go only to hosts and paths they match, so a CDN on another domain doesn't get the site's cookies. What it picks:
  - HLS: the variant with video and the highest bandwidth, plus the audio playlist that variant names (DEFAULT, else AUTOSELECT, else the first).
  - DASH: the video and main audio representations with the highest bandwidth. SegmentTemplate (`$Number$` and `$Time$`, with or without a SegmentTimeline) and SegmentList are read as segments. A representation that is one file (Reddit's BaseURL shape) downloads like a plain file with parallel ranges.
  - Refused with a clear message: live streams, DASH with more than one period, and DRM. HLS AES-128 is decrypted with the key the page's own server serves.

  The first segment's server is probed to pick the protocol: 8 parallel requests over HTTP/2 or HTTP/3, 4 over HTTP/1.1. Busy servers get the same back-off as plain files. Segments are written in order. Fragments waiting for a slow earlier one are capped at twice the parallel requests, which bounds memory. A dropped connection or a 5xx is tried twice more. Each track goes to a file in a hidden work folder beside the final file. FFmpeg then joins the tracks without re-encoding (`-c copy`) into an MP4, or WebM/MKV for WebM tracks, and the work folder is deleted. This is the one exception to "no part files": FFmpeg needs the tracks as separate inputs. Without FFmpeg, a single track is kept in its own container (`.ts`, `.mp4`), and separate video and audio fail with a message saying FFmpeg is needed. The engine looks for FFmpeg next to `engine.exe`, then on PATH; the installer will bundle it.
- **2026-10-12: Streams help each other, and a busy server's limit grows back (Phase 4).** A download still starts with one piece per stream. When a stream finishes, it takes over the back half of the largest piece still in flight, as long as both halves are at least 1 MiB. The slow stream's reply is cut off at the new end, so one slow connection no longer holds up the end of the download. A piece refused with 429 or 503 goes back in the queue for whichever stream is free next. After 30 s without a refusal, a limit lowered by a busy server goes up by one, and it never goes above the plan's 8 streams or 4 connections. If the server refuses again, the limit drops again. Measured on a real server: Tele2 100 MB over 4 HTTP/1.1 connections, and Go's installer over HTTP/3, both complete.
- **2026-10-12: How a download is fetched (Phase 3).** The engine probes again when the download starts, then follows the plan: the file is cut into as many equal parts as the plan has streams (8 on HTTP/2 or HTTP/3 over one connection, 4 HTTP/1.1 connections, or one request). Each part is a range request with `If-Range` (a strong ETag, else Last-Modified). A 200 instead of 206, a different ETag, the wrong `Content-Range` or a short body fails the download; it never finishes with mixed or missing bytes. Real servers limit parallel requests: proof.ovh.net accepts about 3 at once and answers the rest with 429 and `Retry-After: 10`. So a part refused with 429 or 503 releases its slot, the download's limit drops to the number of requests still being served, and the part waits as long as the server asks (5 s if it doesn't say) before trying again. It gives up after 10 refusals or when asked to wait over a minute. The window shows the lowered count. The limit only shrinks for now; Phase 4 grows it again from measurements. A failed or cancelled download deletes its `.part` file, because nothing can resume it until the Phase 5 range log exists. Only plain video and audio files can be downloaded; HLS and DASH need Phase 4. `engine.exe -get URL [-dir D]` downloads from the command line.
- **2026-10-12: How the engine probes a server (Phase 2).** One GET for byte 0 only (`Range: bytes=0-0`, `Accept-Encoding: identity`) over TCP, with the browser's headers, Referer and cookies; TLS ALPN picks HTTP/2 or HTTP/1.1, and redirects are followed. A 206 with `Content-Range` means ranges work and gives the size; a 200 means the server ignores ranges. A compressed reply counts as unknown size and no ranges. If the reply's `Alt-Svc` offers `h3` on the same host, the same request goes over QUIC (5 s limit); HTTP/3 is used only if it answers and describes the same file (size, ranges, ETag). Otherwise it falls back and records why (UDP blocked, other host, different file). Plan: no ranges, unknown size, or under 1 MiB: one request. HTTP/3 or HTTP/2 with ranges: up to 8 streams on one connection. HTTP/1.1 with ranges: up to 4 connections. 429/503 come back as errors carrying `Retry-After`. That's two connections when HTTP/3 is offered, not one: `Alt-Svc` can only be learned over TCP. `engine.exe -probe URL` runs a probe from the command line.
- **2026-10-12: How the extension spots streams (Phase 1).** It watches every tab's requests (`webRequest`, `host_permissions: <all_urls>`) and lists HLS playlists, DASH manifests, and video/audio files whose size is known and is 256 KB or more (unknown-size files were mostly site UI sounds, so they are skipped). Stream segments (`.ts`, `.m4s` and similar) are never listed. A tab's list resets when a new page loads. Nothing goes to the app until the user presses "Send to app". The context sent is: URL, kind, page URL and title, Referer, the request headers worth replaying (not Cookie, Range or per-connection headers), cookies from the browser's cookie stores (including partitioned ones), and the playlist text fetched by the extension. Cookies are read only when sending and are never kept in extension storage. The engine checks each context and refuses DRM streams (`SAMPLE-AES`/KEYFORMAT keys in HLS, `ContentProtection` in DASH) at that point. Received streams are held in memory until downloads exist; SQLite comes in Phase 5.

- **2026-10-12: The open questions were left to Claude's judgement.** The user asked Claude to pick. The five decisions below are those picks.
- **2026-10-12: Go for all native code.** That covers the engine, the Native Messaging relay and the UI backend, so there's one toolchain and one language. Go's standard library covers HTTP/1.1 and HTTP/2. HTTP/3 uses `quic-go`. Rust was dropped: it's harder to maintain for this team, and there was no measured need for it.
- **2026-10-12: Three processes.** (1) `engine.exe`: a background process that starts at login, owns the tray icon, does all downloads, and keeps running when the window is closed. (2) `nmhost.exe`: a small relay that the browser launches. It forwards the extension's JSON messages to the engine and holds no download logic. (3) `ui.exe`: a Wails v2 window (WebView2 + TypeScript), opened from the tray. The engine is the only process that writes files or the database. Why: downloads must survive the UI closing, and Chrome kills the Native Messaging host when the extension disconnects.
- **2026-10-12: IPC is JSON over a per-user named pipe** (`\\.\pipe\InternetDownloader-<user SID>`, via `go-winio`). The pipe's ACL allows only the current user. Nothing listens on a TCP port.
- **2026-10-12: Runs as the normal user, never elevated.** No service and no admin rights. That rules out `SetFileValidData`. Pre-allocation uses `SetEndOfFile`, plus `FSCTL_SET_SPARSE` on NTFS.
- **2026-10-12: Disk writes default to positioned writes (`WriteAt`), not mmap.** mmap stays an option to benchmark in Phase 3. It's adopted only if it's measurably faster with no loss of safety: with mmap, a full disk or a dropped network drive crashes the process instead of returning an error.
- **2026-10-12: FFmpeg is a bundled `ffmpeg.exe`, run as a subprocess** for muxing (`-c copy`, no re-encoding). There's no libav linking, so no cgo and no linking-license obligations. The installer ships the binary with its license and source link.
- **2026-10-12: Chrome, Firefox and Edge are all supported in v1.** The user asked for Firefox: they use Chrome and Firefox, and Edge stays in for other people. There's one MV3 extension codebase. The relay is registered at `HKCU\Software\{Google\Chrome | Microsoft\Edge | Mozilla}\NativeMessagingHosts\com.xoguyfawksxo.internet_downloader`. Chrome and Edge share a manifest that uses `allowed_origins`. Firefox has its own manifest that uses `allowed_extensions`, with the add-on ID `internet-downloader@xoguyfawksxo`. The relay tags each message with the browser and extension that sent it.
- **2026-10-12: Public GitHub repo, GPL-3.0, same as the TuneUp Suite.** CI minutes are free, and the license works with a GPL FFmpeg build. The name is `internet-downloader` until the user picks one. Creating the repo still needs the user's go-ahead.
- **2026-10-12: Windows 10/11 x64 only for v1.** The Go code keeps OS-specific pieces (pipe, pre-allocation, tray, registry) behind small interfaces, so a later port doesn't need a rewrite.

- **2026-10-12: Protocol priority is HTTP/3, then HTTP/2, then HTTP/1.1 ranges, then a single stream.** Multiplex on one connection when the server allows it; fall back to multiple TCP connections only for HTTP/1.1 with `Accept-Ranges`; download in one stream when ranges aren't supported.
- **2026-10-12: Default limits: 8 logical streams, 4 physical TCP connections per download.** These are ceilings; the adaptive controller may use fewer.
- **2026-10-12: One output file per download, pre-allocated, written at byte offsets.** No part-files joined at the end.
- **2026-10-12: Progress is tracked per byte range in SQLite (WAL mode).** Resume restarts only uncommitted ranges.
- **2026-10-12: The browser extension sends a full context object** (URL, cookies, headers, Referer, manifest text) over Native Messaging, not just a URL.
- **2026-10-12: No DRM circumvention.** DRM-protected streams are detected and refused with a message.
- **2026-10-12: Plain language, measured numbers only.** No invented speeds, counters or marketing claims in the UI, README or docs.
