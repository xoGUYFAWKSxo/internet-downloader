```
Browser extension (HLS/DASH sniffer)
   | Native Messaging (JSON context object)
   v
App orchestrator --> Network engine (HTTP/3 -> HTTP/2 -> HTTP/1.1 ranges -> single stream)
                        |

                        |
                     SQLite WAL progress log (per byte range)
```

## Technical notes to check before building (corrections to the original plan)
- **HTTP/3 discovery isn't ALPN on the first connection.** A client learns a server speaks HTTP/3 from the `Alt-Svc` header (or HTTPS DNS records), after a TCP+TLS connection. ALPN chooses between HTTP/2 and HTTP/1.1. Phase 2 should probe over TCP, read `Alt-Svc`, then try QUIC and fall back if UDP is blocked.
- **`SetFileValidData` needs admin rights** (SeManageVolumePrivilege) and exposes whatever old data was on the disk in that space. It also doesn't make a sparse file. For a non-elevated app, use `SetEndOfFile` (optionally with `FSCTL_SET_SPARSE`) or `SetFileInformationByHandle(FileAllocationInfo)`.
- **mmap isn't zero-copy for network data**: bytes are still copied from the socket buffer into the mapped pages. On Windows, a disk-full or network-drive error while writing to a mapping becomes an access-violation crash rather than a normal error. Plan: benchmark mmap against positioned writes (`WriteAt`) in Phase 3 and pick by measurement; keep the safer one unless mmap is clearly faster.
- **MV3 `webRequest` can observe but can't read response bodies.** The extension must fetch the manifest itself (or the engine fetches it with the forwarded cookies/headers).
- **Native Messaging host** is registered per browser under HKCU (Chrome, Edge, Mozilla) `\NativeMessagingHosts\<name>`. Firefox launches the host with the manifest path and the add-on ID as arguments; Chromium launches it with the extension origin. messages are length-prefixed JSON, max 1 MB from host to browser (64 MiB from browser to host).

## Resume (Phase 5)
The engine keeps the download list in `%LOCALAPPDATA%\InternetDownloader\downloads.db` (SQLite, WAL mode, `internal/journal`, pure-Go `modernc.org/sqlite`, so no cgo). Every 3 seconds a running file download flushes its file to disk, then commits the byte ranges written before the flush. A dropped connection (or a 502, 503 or 504 the per-request retries didn't get past) pauses the download, which tries again after 5, 15 and 45 seconds. Each try probes again and carries on only if the size and the ETag or Last-Modified are unchanged; only the ranges not committed are requested. Quit pauses file downloads, and after a crash they come back paused, with Resume and Discard buttons. A file without range support or a validator can't be resumed and starts over. Streams (HLS/DASH) still start again: after Quit or a crash they show as failed, and their unfinished file and work folder are deleted at the next start. The request (cookies included) is kept in the database only while a download can be resumed, and wiped when it ends. The list keeps the last 200 downloads.
- Tests: a reopened `.part` keeps its spans; only missing ranges are fetched; dropped-or-not classification; the journal survives a reopen (in a folder with a space and an apostrophe) and `End` wipes the cookies; two connections cut mid-piece are retried and the first piece carries on from 512 KiB; Quit pauses a download at 4 MiB, a new engine restores it as paused with 4 MiB done, and Resume finishes it byte-identical without asking for the saved pieces; after a simulated crash a file download is paused, a stream's `.part` and work folder are deleted, and Discard deletes the file and wipes the saved request.

## Window (IDM-style, step 1)
The window looks like IDM's main window: a toolbar (Add URL, Resume, Stop, Stop All, Delete, Delete Completed), a category list (All Downloads with Compressed, Documents, Music, Programs and Video by file extension; Unfinished; Finished; Sent from Browser, which holds the old received-streams list), a table (File Name, Size, Status with a small progress bar, Time Left, Transfer Rate, Date Added) and a status bar (engine state, number of downloads and running ones, total speed). Columns sort by clicking the header and can be resized by dragging; widths, sort and the chosen category are remembered. Rows select like Explorer (click, Ctrl, Shift, Ctrl+A, arrow keys). A right-click menu has Open, Open folder, Resume, Stop and Delete; double-click or Enter opens a finished file; Del deletes. Stop pauses a file download and keeps what is in (`downloads.pause`); a stream can't pause, so Stop cancels it. Delete takes downloads off the list and the saved list (`downloads.remove`), deletes a paused download's unfinished file, and deletes finished files only when the box is ticked; running downloads have to be stopped first. Add URL (`downloads.add`) takes an http or https address, filled in from the clipboard when it holds one; no cookies are sent. Time Left is worked out from the measured speed only and is blank until there is one.
- Tests: Stop pauses with the file kept, a second Stop is refused, Resume finishes byte-identical; Delete leaves a running download and reports it, deletes a paused download's `.part`, deletes a finished file only when asked, and removes the rows from the database; Add URL refuses empty, `file:`, `ftp:`, host-less and non-address input.

## Progress window (IDM-style, step 2)
Double-clicking an unfinished download (or Progress… in the right-click menu) opens its progress window: status, file size, downloaded with percent, measured transfer rate and time left, resume capability (Yes/No, or not known until the server has been asked), and the server (host only, protocol, parallel requests while running), with a progress bar and Pause/Resume and Close; a finished download shows Open and Open folder. "Show details" adds a map of the file (written parts, what each connection still has to fetch, and where each one is writing) and a connections table (N., bytes it has written, what it is doing: connecting, receiving, waiting for a free slot, server busy, finished). Each progress window is its own `ui.exe --progress=ID` process, since Wails v2 has one window per process; opening it again brings the open one forward. The engine's `downloads.detail` call gives the status, written spans and streams; `fetch.Watch` reports the streams of a running download. Streamed video (HLS/DASH) shows its segment count instead of the map and table.
- Tests: `fetch.Watch` lists each stream's piece and bytes while the download runs, covering the file between them, and nothing after; `downloads.detail` refuses an unknown id, shows streams and written spans (at least what is reported done) while running, the kept spans and no streams once stopped, and the whole file once done; `--progress=` parsing.
- Checked by hand (2026-10-12, `wails dev` page against the new engine and a slowed local server): a 400 MB download showed 4 connections receiving with matching bytes, 5.0 MB/s and a time left; Pause stopped it at 65.5% with the map keeping the written parts and no connections open; Resume carried on from there.

## Queue, scheduler, speed limiter and Options (IDM-style, step 4)
One queue, like IDM's main queue. Download Later in the Download File Info box puts the link at the end of it; "Add to queue" on the list's right-click menu adds a stopped download that can be resumed, and "Remove from queue" and "Move up/down in queue" change it. Start Queue (toolbar or tray) runs it in order, a set number at once (Options, 1 to 10, default 2); it stops by itself when nothing is left to start. A queued download that is paused by hand or fails isn't started again until the queue is started again; one that can't be resumed any more leaves the queue. Stop Queue pauses the queue's running downloads (one whose server can't resume is left to finish). The queue's order is kept in the saved list (in the status JSON), but the queue doesn't start by itself when the app starts.
- Speed limiter: one token bucket (`fetch.Limiter`) shared by every download, files and stream segments, in KB/s. Reads are cut to 1/8 of a second's worth so progress stays smooth; changing the rate releases waiting readers at once. On and off from Options or the tray menu; the status bar shows the limit.
- Scheduler: start the queue at a time on chosen days, and optionally stop it at another time, checked every 15 s while the engine runs. A time missed by more than 5 minutes (the computer was asleep) is let go; it doesn't wake the computer.
- Options window: `ui.exe --options[=tab]`, tabs General (both boxes on/off, download folder), Speed limiter, Queue, Scheduler; the toolbar's Scheduler button opens the last tab. It saves all settings or none (`settings.save`). The Download folder is now also where downloads go when the box is off. The tray menu's two box ticks were replaced by Start/Stop the queue, Limit download speed and Options…
- Tests: limited downloads over ranges and over a single stream take at least size/rate and arrive whole; turning the limit off or cancelling releases a waiting reader; the queue runs in its order with moves applied, one at a time, a 404 download fails and leaves the queue without stopping it, and the queue stops when done; two at once under a 64 KB/s limit, a third waits, a hand-paused one is replaced and not restarted, Stop Queue pauses the rest and keeps them queued, remove and add again puts one at the end; bad settings refused all-or-nothing; streams can't be queued; the scheduler's start and stop times, days, midnight and a late wake.
- Checked by hand (2026-10-15, installed build, slowed local server): Options opened at the Scheduler tab from the toolbar, saved a 512 KB/s limit and one at a time; two Add URL links went to the queue with Download Later; Start Queue ran the first at a measured 517 KB/s while the second showed Queued; pausing the first started the second; Stop Queue paused it with both still queued; the right-click menu showed the queue items. The test downloads were deleted and the settings put back afterwards.

## Release build
`installer/build-release.ps1 -Version X.Y.Z` builds `dist/release/GalacticDownloader-X.Y.Z-setup.exe` (Inno Setup 6, about 38 MB), the extension zipped for Chrome/Edge and for Firefox, and `SHA256SUMS.txt`. The programs carry the version (the engine's `ping` answer, the window's file properties, the extension's manifest). FFmpeg 9.0.2 (Gyan's essentials build) comes from a pinned URL and is checked against its SHA-256, which matched the one gyan.dev publishes; its licence, readme and where its source is go in beside it, and `THIRD-PARTY-NOTICES.txt` collects the licences of the 26 Go modules built in. The installer is per user with no admin rights, into the same folder as `install.ps1` (so it upgrades a development install), adds an Apps & Features entry, Start Menu and optional desktop shortcuts, and registers the relay in HKCU with manifests beside `nmhost.exe` that name it by a relative path. The `release` workflow runs it on a `v*` tag into a draft release, and on PRs that touch the release build as an artifact.
- Checked on this machine (2026-10-15) with the installer CI built: a silent install over the running development install closed the engine and window and replaced the files; the relay, started from each manifest as Chrome and Firefox do, started the engine from the install folder and answered `ping` with the stamped version; `ffmpeg.exe -version` ran.
